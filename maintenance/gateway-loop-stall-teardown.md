# Gateway loop stall and teardown exit

**Patch identity:** `gateway-loop-stall-teardown`

## Invariants

- Async gateway handlers never take the synchronous session-store lock on the event-loop thread.
- Persisted model-override hydration reads occur in a worker and commit through the existing epoch/edit-pending compare-and-set fence.
- Session-store routing peeks reachable from async status, heartbeat, topic, webhook and API paths run off-loop.
- Gateway teardown cancels pending tasks and shuts down async generators with a three-second total budget (two seconds for tasks, one for generators). It never joins the default executor or lingering non-daemon workers.
- API session-model workers use read-only, CPython-GIL-atomic single dictionary lookups of the loop-owned session view; they never iterate, create state, mutate overrides, or perform a worker-side compare-and-set. The epoch/edit-pending fence fails closed if a loop-owned edit races the fallback read.
- New Telegram topic setup uses `AsyncSessionStore` for creation/title writes, `to_thread` for binding/reasoning sync writes, and async route resolution; it does not add a loop-thread store lock.

## Implementation

`GatewayTurnMixin._rehydrate_session_model_override_async` owns the async hydration path. It serializes with the per-session asyncio lock, calls `_load_session_model_override` through `asyncio.to_thread`, and uses `_commit_session_model_override` with the captured epoch. `/status`, `/model`, topic model selection and async model resolution use that path. The model-switch context does not rehydrate synchronously again when no persisted override exists. Both typed and picker `/fast` writes run off-loop, with session state created on the loop before offload. Eligibility and the route-ignored warning use a route resolved on the loop by the async runtime resolver (the picker re-resolves at selection time) and passed into `_apply_fast_selection`, so the worker never resolves or commits route state for any tier. API session chat, completions, responses and run creation hydrate through `SessionModelRoutesMixin` on the loop before offloading validation. Synchronous API override lookup uses read-only snapshots/loads, never get-or-create or a worker-side CAS. `/v1/runs` `_execute_run` reads that snapshot in a worker and passes it to `_create_agent` (`session_override_snapshot`), so on-loop agent creation never reads the store; other `_create_agent` callers already run in workers and keep the lazy read. Routing peeks in heartbeat ownership/polling, heartbeat restore, Telegram topic existence and webhook completion use worker threads.

`gateway.run.main` and `hermes_cli.gateway.run_gateway` use `gateway.event_loop.run_until_teardown`, a private event loop that cancels pending tasks, waits at most two seconds for their cleanup, then allows at most one second for `shutdown_asyncgens`. It uses `asyncio.wait`, not `wait_for`, so cancellation-resistant tasks/finalizers cannot extend the deadline. `_persist_session_model_override_locked` registers its shielded write through `create_teardown_write`: cancellation reaches the owner but does not cancel its durability child. Both get the same bounded task budget. After cleanup the existing hard-exit funnel runs without `shutdown_default_executor`, avoiding `asyncio.run`'s stuck-worker join. A task or write that outlives the budget is abandoned at hard exit; the backstop never waits indefinitely.

## Verification

Focused tests run through `HERMES_PYTHON=<test-env>/bin/python bash scripts/run_tests.sh <one file>` under `heavy-slot`: `tests/gateway/test_session_store_loop_boundaries.py`, `tests/hermes_cli/test_gateway_run_hard_exit.py`, `tests/gateway/test_gateway_process_exit.py`, `tests/gateway/test_session_model_override_persistence.py`, `tests/gateway/test_loop_thread_statedb_sites.py` and `tests/gateway/test_running_agent_session_toggles.py`. The boundary suite needs the `messaging` extra (`aiohttp`) for API/webhook cases. It checks loop-owned cold state and hydration commits, direct webhook/turn-heartbeat peeks, and real child processes with blocked default-executor jobs and lingering non-daemon threads. The hard-exit suite checks a cancellation-finally write, async-generator finalization, an in-flight shielded model-override state.db write, and bounded teardown with cancellation-resistant tasks/finalizers. Exit sentinels close their private test loops.

The new-topic first-turn audit found session creation and turn markers already use `AsyncSessionStore`, bindings use the async DB facade / `to_thread`, and reasoning settings use the existing off-loop applier. Title callback attachment happens in `GatewayTurnRunner`'s synchronous worker; title/icon generation is not an event-loop-side prerequisite for launching the agent. Renames and icon persistence cross async/off-loop boundaries. The guarded first-topic setup test covers route creation, binding and session-open preparation; it does not reproduce the historical 5–7-minute delay under load.

The existing live gateway CPU samples were read-only. The three native `sample` captures show 405, 411 and 494 threads with dominant condition/GIL waits and I/O waits; the middle capture sampled all 110 main-thread stacks reacquiring the GIL after `kqueue`. That supports thread/GIL contention, not a proven gateway busy loop or an identified provider hot function. The samples do not identify the exact source of sustained >1-core CPU; no CPU change is included.
