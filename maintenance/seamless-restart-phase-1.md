# Phase 1: durable cron execution and seamless gateway restart

Status: implementation approved, **not implemented**. Land Phase 0 restart fixes first. Do not start Phase 1 code until the macOS launchd bootout experiment and Phase 0 are reconciled with current main. Each slice below is a separate, independently mergeable PR based on the preceding slice. No slice itself authorizes a live gateway update/restart.

## Current evidence and constraints

- A disposable macOS launchd experiment found that `launchctl bootout` without `AbandonProcessGroup` killed a plain child, but a `start_new_session=True` child and a double-forked `setsid` grandchild survived. With `AbandonProcessGroup=true`, all three survived. This demonstrates process-group, not all-descendant, teardown for that experiment; test the production launch path before generalizing. A September 1 updater child reportedly died with its gateway: determine whether it shared the process group or was killed via `kickstart -k`/another supervisor path; do not erase that contradictory observation.
- `tools/process_registry.py::restart_safe_gateway_child_argv` currently takes the Linux/systemd path only and returns `in_process` on macOS. `cron/scheduler_detached_worker.py` already exists. `cron/scheduler.py` tracks running worker PIDs and `cron/executions.py` holds the execution ledger; its inactivity watchdog does **not** bound active but indefinitely running work. `recover_interrupted_executions` must distinguish live detached workers from dead ones.
- `gateway/control_socket.py` implements a gateway-owned local control surface related to [upstream issue #92091](https://github.com/NousResearch/hermes-agent/issues/92091). Extend this surface for generation-aware handoff rather than adding another PID/argv-based controller. `gateway/turn_lease.py` and the Telegram credential-scoped token lock are ownership primitives to reuse; no two `getUpdates` pollers may own a token simultaneously.
- [Fork/upstream PR #123893](https://github.com/NousResearch/hermes-agent/pull/123893) is open and retains the outgoing gateway PID in its restart snapshot. Reconcile it before changing fleet identity or observer behavior; do not race or duplicate that change. [PR #123878](https://github.com/NousResearch/hermes-agent/pull/123878) was closed **in favor of merged salvage [#124009](https://github.com/NousResearch/hermes-agent/pull/124009)** (`8afaab3703e336d72a72c812dd2dd249f04f166a`), which preserves author credit and adds infinite-drain handling. Retain its restart wait envelope rather than reintroducing a 15-second observer cut-off.
- Existing `restart_drain_timeout: 0`, `cron_drain_timeout: 0`, and `restart_resume_policy: continue` cannot protect long work through a stop/start. Phase 1 adds durable process/release ownership, not a longer synchronous drain.

## Delivery order and acceptance

### PR 1 — macOS restart-safe detached cron child

Enable a genuinely detached new-session worker on macOS in `tools/process_registry.py`, following the existing Linux restart-safe selection contract but without pretending systemd scopes exist on macOS. Route gateway-owned cron executions through `cron/scheduler_detached_worker.py`; preserve profile home, secret scope, job identity, execution ID, cancellation/stop ownership, and delivery semantics. Do not set `AbandonProcessGroup` on the production job as a shortcut: it also abandons plain descendants. Ensure an orphaned worker has a separately supervised hard wall-clock kill-after-timeout, distinct from the inactivity watchdog, with PID + process start-time identity and a terminal ledger outcome. No automatic retry of an interrupted attempt that may have side effects.

**Acceptance:** host-native macOS test launches a real worker as a new session, boots out only a disposable parent launchd job, proves the worker survives and ultimately exits or is killed at its configured hard deadline. A normal long cron run completes exactly once. Linux/systemd and Windows paths retain their existing behavior. This slice must not claim update-safety yet: code still runs from a mutable checkout.

### PR 2 — immutable releases and pinned workers

Stage a verified full commit SHA into immutable `releases/<sha>/` with an environment bound to the release. Reuse an existing venv only when the complete dependency/lock/install inputs are unchanged; otherwise stage a fresh one. Atomically switch `current` only after validation, keep the last three releases (and any older release still referenced by a live worker), and provide rollback without editing a live release. Cron workers must execute from the absolute release they started on; new runs resolve `current` once at admission. Never lazily import from the in-place checkout across an update. Add `code_sha` to `cron/executions.db` at claim time, including a compatible migration and readback API. Shared job stores/DBs, ledgers, and `~/.hermes/plugins` must be readable and writable by current **and previous** releases; incompatible changes fall back to stop/start, not forced overlap.

**Acceptance:** stage two distinct SHAs with identical and changed dependency inputs; verify environment reuse only for the former, atomic pointer/rollback, three-release retention plus live-reference protection. Start a long detached cron under old SHA, promote `current`, prove its result and code provenance remain old while the next occurrence uses new SHA exactly once. Assert old/new DB and plugin compatibility before promotion.

### PR 3 — worker completion, delivery, and recovery across downtime

Specify one durable ownership protocol for a detached worker's terminal result: either it can deliver independently using a pinned transport with bounded retries, or it writes an idempotent delivery outbox row that the successor gateway claims. Prefer the existing delivery ledger/queue rather than a second transport owner. The gateway must not mark a **live** detached worker `unknown` in `recover_interrupted_executions` merely because its parent died. Track `(PID, start-time, execution ID, release SHA)` and a durable heartbeat/claim; reconcile dead/orphaned workers honestly. Keep the release until terminal execution **and** delivery settle. Unknown external send outcomes remain unknown, never blindly retried. Bound orphan life with the hard deadline introduced in PR 1.

**Acceptance:** run a genuinely long cron job across an instantaneous gateway update/outage; it survives, completes, and delivers once after the successor arrives, with terminal execution and delivery receipts and old `code_sha` in `executions.db`; the next occurrence runs once under the new SHA. Crash before and after external delivery acknowledgement, kill a hung orphan, and prove no duplicate side-effect retry or false interrupted recovery. Use temporary profile homes, not live stores.

### PR 4 — overlapping gateway admission and handoff

Start the candidate from its immutable release under a **second launchd label** and distinct control socket, status identity, and process-generation ownership. Existing single-name `gateway.sock`/PID/status assumptions cannot be reused concurrently. Stage and validate, then atomically transfer admissions: stop old Telegram polling and release its credential-scoped token lock before candidate `getUpdates` starts; fence per-profile cron tick ownership and the embedded Kanban dispatcher so only one generation schedules/claims new work. Old generation retains outbound delivery and owns its in-flight turns/cron. Route `/steer`, approvals/denials, stop, and queued follow-ups through the new gateway to the old `gateway/turn_lease.py` owner with an authenticated, acknowledgement-bearing control protocol; preserve both busy-message guards, session identity, ordering, and user authorization. A new gateway's receipt means the old owner accepted it, not merely that forwarding was attempted. Refuse or durably retain on forwarding failure.

Give the candidate a real health check (including a messaging round trip and exclusive lock/ticker ownership) within about 60 seconds. On failure, fence candidate admissions, transfer ownership back and verify old service, and atomically roll back `current`. Cap old-gateway coexistence at about two hours; terminate unresolved work with an honest terminal/unknown state and keep its pinned release until durable settlement. If shared-schema/plugin compatibility preflight fails, use an announced stop/start update. No automatic retry of interrupted model/tool runs. Record candidate/old SHAs, generation, transfer, health, rollback, and timeout in an update receipt. Preserve #124009's restart-wait semantics and incorporate #123893's outgoing identity if it merges.

**Acceptance:** integration test with two disposable launchd labels asserts exactly one Telegram `getUpdates` owner and one cron/Kanban admission owner throughout promotion/rollback, forwards in-flight steer/approval/follow-up to the old process, and delivers its answer. Candidate health failure rolls back within ~60 seconds. An incompatible plugin/schema forces stop/start. A two-hour fake-clock bound retires old admission without replaying side effects. Full golden path repeats the PR 3 long cron, delivery ledger, old SHA and next-new-SHA checks during overlap.

## Open decisions before each slice

- Is the production updater in a new session on macOS, and was September 1 `kickstart -k`, plain-child process-group inheritance, or another path? Reproduce with disposable labels only; no production `bootout` test by implementers.
- Should delivery use a detached worker's own transport or the existing durable gateway outbox? Resolve credential-scoped locks, the period without a gateway, exactly-once admission versus unknowable external-send outcome, and plugin compatibility before PR 3.
- Where should the supervised orphan timeout and process-start fingerprint live so a gateway restart cannot reset the hard deadline? Define policy/config and terminal classification before PR 1.
- How are `current` and release directories integrated with the existing in-place fork installer and rollback, and which shared DB/plugin migrations can truly support N and N−1 concurrently? A compatibility rejection must be actionable.
- What authenticates generation-specific local sockets and fences an old gateway after the second label takes admission? Define a crash-recovery handshake rather than inferring ownership from PID liveness alone.
