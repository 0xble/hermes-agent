# Runtime Epoch Owner Fence

Load when changing `begin_runtime_epoch`, `initialize_session_authority`, profile ownership reservations, the `tests` package import, or the runtime status fields readiness reads.

Patch identity: `runtime-epoch-owner-fence`.

## Required Behavior

- `begin_runtime_epoch` refuses with `OwnershipConflict` while another process holds a runtime lock (`gateway.lock` or `gateway.b.lock`) of the store's home. Each slot this process does not hold is probed, including the sibling of a slot it does hold, because a flock probe from the holder's own process would read its own reservation as held. Reservations anywhere in this process count by slot (`process_ownership`, an `exclusive_maintenance` reservation of both slots on any thread, an embedded `ProfileOwnership`). A slot-holding caller may begin beside a sibling that answers its own status as an unpromoted standby, which begins no epoch. The only other allowance is `successor=True`, passed by the zero-cut promotion alone, whose predecessor slot still holds its lock while it finishes its turns. A home nobody holds stays open: the offline dashboard edit and temporary test homes begin as before, and the next owner's own begin supersedes such an epoch.
- Slot role resolution treats an unanswered sibling status query as standby while the sibling holds its lock. Otherwise a slow serving slot a would let slot b boot active and take a's epoch.
- A zero-cut standby begins no epoch at boot. Slot b reserves `gateway.b.lock` beside a serving slot a, so the foreign-owner check cannot stop it. `initialize_gateway_runtime` therefore builds its authorities unclaimed (`UNCLAIMED_EPOCH = 0`: every fenced write fails `stale_epoch`) and skips Bot Chat recovery. A standby also refuses `serve-profile` and `rescan-profiles`. Promotion calls `claim_gateway_runtime`, which claims the launch profile first, then each secondary, then runs Bot Chat recovery. The launch claim is the point of no return, so a secondary that fails after it is parked the way boot parks one, and only a launch failure aborts the promotion. A claim is resumable: a retry after a step raised reuses the epoch it already began and reruns the remaining idempotent steps. `epoch_claimed` is set only after the last of them. A retry first checks that the store still holds that epoch. After a rolled-back promotion slot b answers standby, so slot a may restart and begin a newer epoch. The retry then claims again instead of serving on the stale one. After the claims, the served set is re-recorded against the registry, so a profile parked during promotion never gets adapters from the boot-time served set. Before this, slot b's boot staled every write of slot a and recovered a's running turns as `unknown`. After promotion, a's last in-flight settlements still meet b's epoch. The single store epoch cannot fence 2 live owners, so that overlap remains part of the zero-cut handover contract.
- `slot_lock_held` fails closed. A lock file that exists but cannot be opened is reported held, as `is_gateway_runtime_lock_active` does. `slot_lock_state` reports `unknown` only for a `PermissionError`. Other open errors such as EMFILE are transient and read as `held`. The promoted slot's predecessor wait polls through `held`, and through `unknown` while the predecessor slot still answers its control socket. It goes on once an unopenable predecessor stops answering.
- Importing the `tests` package exports `HERMES_TEST_ISOLATION` (setdefault). A direct `python -` probe that reuses a test helper therefore arms the live-DB guard and fails at its first production `SessionDB()`. Under pytest the conftest replaces the value with its sandbox home.
- `initialize_session_authority` names the store-open failure (the runner's handle-cache error) instead of failing on `None.db_path`.
- The gateway housekeeping chore `Runtime epoch watch` compares each live authority's epoch with the store's. A move while this process still holds the profile logs CRITICAL once per taken epoch (naming the writer's instance id) and publishes `runtime_epoch: {"status": "lost", "held": N, "store": M}`. Readiness then reports `runtime_epoch: unavailable`. It never re-claims the epoch: the writer may still be running, and the recovery a begin runs would mark this owner's running turns `unknown`. A gateway treats the move as its successor's promotion, logged at INFO once, only when it accepted a zero-cut handover that has not failed and the new holder's instance id is the one its sibling slot's `identify` answer publishes. During such a handover a sibling that does not answer is pending, rechecked each tick, and reported only after `HANDOVER_PENDING_TICKS` (5) unanswered ticks. A busy promotion therefore never draws a CRITICAL "restart" advice mid-handover. Each start publishes `runtime_epoch: ok`, so a reloaded `lost` from the previous run does not outlive it.
- The `tests` marker deliberately reaches the probe's children through the environment. The #82770 escape was a child that lost its parent's isolation, and the conftest marker inherits the same way.

## Incident

On 2026-10-30 at 6:25 PM PT a delegated review agent ran a `python -` probe from a fork worktree. It imported `_busy_owner` from `tests/gateway/test_busy_burst_serial_reader.py`, whose `initialize_session_authority(instance_id='owner')` began epoch 36 on the live `~/.hermes/state.db` while the gateway held 35. The probe inherited the gateway shell's `HERMES_HOME`, ran no conftest and had no pytest ancestor, so the live-DB guard stayed disarmed. Its startup recovery also turned the gateway's started admissions `unknown`. Every later settlement failed `stale_epoch` until a manual restart. AGENTS.md already forbade such probes, so this patch enforces the rule in code.

## Verification and Retirement

`tests/hermes_state/test_direct_probe_isolation.py` runs the probe shape in a child with a temporary `HOME` and pytest ancestry pinned off. `tests/hermes_state/test_runtime_epoch_foreign_owner.py` holds the lock from a second process and covers in-process and maintenance reservations. `tests/gateway/test_runtime_epoch_watch.py` covers the once-only CRITICAL, the published status, released ownership, readiness, and the handed-over sibling with and without a live sibling lock. `tests/gateway/test_zero_cut_standby_epoch.py` boots a real standby runner beside slot a's epoch and claims at promotion. It also covers a secondary claim failure that parks the profile, a retried half-claimed promotion, the unanswered role query, the standby's profile verbs and an unopenable predecessor lock. The foreign-owner suite runs with the holder on each slot's lock and with an unopenable lock, and covers a slot-b reservation beside a serving slot a, an active slot beside a standby, and a lock-less successor claim. Each of the first two fails on the base revision, and the watch suite does not import there.

Retire when upstream fences epoch begins on profile ownership and reports a lost epoch, and these regressions pass without the local implementation. Reverting changes no schema or stored data.
