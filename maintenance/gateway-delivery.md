# Gateway delivery, receipts and chat budgets

This responsibility covers live adapters, final/progress transport, generation ownership and per-chat rate limits. The [root contract](../MAINTENANCE.md)
requires it on every run and owns shared adoption/publication policy.

## Coupled current adaptations

Positively acknowledged partial text sends retain their undelivered suffix
through inline retries, existing fallback routes and durable failure settlement.
The ledger updates failure state and remaining payload together only when the
expected payload, current process owner and nonterminal state still match.
Producer and startup recovery both use that settlement, so a later failure with
no new chunk metadata cannot restore an acknowledged prefix. Timeout on a suffix
attempt retains the existing no-inline-resend rule. This extends the HERMES-004 /
HERMES-085 boundary with real receipt, SQLite and startup regressions in
`tests/gateway/test_delivery_retry_suffix_durable.py`. No schema migration is
needed. Existing marked at-least-once recovery for genuinely unknown/crashed
sends remains unchanged; this does not promise global exactly-once delivery.
Rollback preserves the existing ledger payloads and reverts the coupled retry
and failure-settlement changes together.

### HERMES-084 — Bound per-chat typing indicator traffic

- **Summary:** Keep the per-thread refresh cadence but bound the CHAT's aggregate typing rate across every session sharing it, and shed any tick that cannot afford budget rather than queueing it. Copying the `_progress_edit_clock` shared-interval shape directly would be wrong: a progress bubble is an idempotent state update, whereas typing is a decaying lease the platform expires after ~5s and renders per THREAD, so round-robining one clock across N threads would refresh each bubble every N*interval and kill all of them. Typing is cosmetic and is therefore the correct traffic to shed first, ahead of progress edits and far ahead of the final answer. Raise the refresh interval to 4.0s, which stays under the ~5s expiry while halving baseline volume, and route `send_typing` through the per-chat send cooldown so a published flood window quiesces typing instead of extending it. The floor is a per-chat gap rather than a per-session one, so N concurrent sessions in one chat get one slot between them. **Superseded in part by HERMES-137 (2026-09-10):** the floor was `min(_TYPING_CHAT_MIN_GAP_S, interval)`, which honoured any caller's cadence over the chat's ceiling and, at the production 4.0s interval, collapsed to the 1.0s constant and let roughly four concurrent threads stack to 60 chat actions/min — a whole private-chat budget spent on a cosmetic indicator. It is now `max(floor, interval)` over a chat-class-aware floor. The rest of this contract (shed rather than queue, per-chat rather than global, routing `send_typing` through the send cooldown, tolerating bare adapters) is unchanged. Bare adapters built without `__init__` keep typing rather than losing the indicator to an `AttributeError`.

### HERMES-085 — Defer flood-controlled delivery obligations

- **Summary:** Classify the parameterised `flood_control:<wait>` class as runtime-retryable alongside the existing exact allowlist, rejecting garbage suffixes rather than raising. Park one coalesced deferred sweep per adapter identity for when the server's stated wait elapses, waking 1s outside the window rather than racing its boundary. ### HERMES-137 — Size the per-chat outbound budget from the chat ceiling

- **Cause and contract:** Telegram meters per CHAT, and every Bot API call spends that one budget: `sendMessage`, `editMessageText`, `sendChatAction`, `deleteMessage` alike. The fork ran two limiters that each believed they owned the whole envelope. HERMES-004's send gate used a flat 1.1s gap for every chat (54 calls/min) and HERMES-084's typing floor resolved to 1.0s under the 4.0s interval (60 calls/min) on `_reserve_gap=False` ticks that never touch the send gate, so one chat could take ~114 calls/min against a private chat's ~60 and a group's ~20. On 2026-09-10 a DM (`2027045491`) took a 7728s ban — 2h09m — while its visible send+edit rate was 8-12/min; the hidden half was the typing loop, which logs successes only at debug. Delegation cards (2026-09-08) did not create the flooder, they lengthened its exposure: turns fanned out to 2-4 concurrent tasks over 25+ minutes, and daily flood events went 12, 2, 0 before the cards landed to 37 and 72 after. Two published cooldowns that day (0.6s at 01:26, 0.7s at 10:49) preceded the ban and were spent without widening anything.
- **Contract:** One per-chat budget, sized from the chat's ceiling and shared by every limiter that spends it. The gap is chat-class aware, taken from the id's sign because Telegram gives groups, supergroups and channels negative ids and needs no extra `getChat`: 2.0s private / 6.0s group for sends, with a 3.0s floor for edits (an edit carries only the latest state, so spacing it costs a reader nothing) and 4.0s private / 12.0s group for typing. Those sum to 45/min against a private chat's ~60 and 15/min against a group's ~20, deliberate headroom because Telegram calls the limits unspecified, adapts them under load, and escalates the penalty on repeat offence. Any published `retry_after` widens that chat's gap by `send_penalty_factor` for `send_penalty_window_seconds` (2x for 10 minutes), scoped to the offending chat and expiring on its own rather than latching. The widening starts with the NEXT call: on the call that published the `retry_after` the server's own number governs, because stacking the multiplier on top of the deadline the server just named would inflate the inline retry past what it asked for (caught by `tests/gateway/test_telegram_send_path_health.py`, which pins the inline sleep to the server's value). The inline-wait cap keeps its purpose of refusing to sleep off a multi-thousand-second server penalty, but is floored at the chat's own routine gap so a group's spacing is waited out instead of surfacing as a retryable flood error. Progress edits and delegation cards are retuned from 1.5s to 3.0s to match the transport floor: a producer faster than the transport does not deliver more updates, it parks each edit inside the chat's send lock ahead of real messages. Every value is overridable through `PlatformConfig.extra`; bare adapters built without `__init__` keep working.
- **Upstream tracking:** Reported as [NousResearch/hermes-agent#107612](https://github.com/NousResearch/hermes-agent/issues/107612) (2026-09-10), which frames the missing shared per-chat budget as its own defect: upstream has no per-chat Telegram send gate at all, and the two open fixes in the area are each sized against the full ceiling independently. Extends our own open report [#99643](https://github.com/NousResearch/hermes-agent/issues/99643), which named the typing loop as a per-chat flood source but not the arithmetic that lets two limiters each spend the full envelope; its volunteer PR [#99676](https://github.com/NousResearch/hermes-agent/pull/99676) has been open and unreviewed since 2026-09-01 and would land the same `min(constant, interval)` collapse, so the finding is noted there too. Open #76494 and #89962 enumerate concurrent flood sources without the budget analysis. Independent open [#107133](https://github.com/NousResearch/hermes-agent/issues/107133) (2026-09-10, reporter `cdepuy`) shows the same install class taking ~5.6h and ~4.3h bans from same-chat session fan-out: a different ignition source that this contract mitigates but does not fix, since N concurrent finals still contend for one chat's budget. All-state searches for `AIORateLimiter`, `rate limiter telegram`, `typing indicator rate limit`, and `editMessageText flood` on 2026-09-10 returned no upstream implementation.
