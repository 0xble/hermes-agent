# Seamless Restart Phase 1 Implementation Plan

Patch identity: `seamless-restart`.

> **Status (2026-09-27):** S1–S3 shipped on fork `main` and run live on this Mac; S4 is not started. See [Shipped Status](#shipped-status). Later changes still follow repository policy, specialist instructions, verification, review, and delivery requirements.

**Goal:** Promote a new Hermes gateway release without interrupting active cron executions or in-flight conversations, while making failure and rollback observable.

**Architecture:** First detach macOS cron workers from the launchd gateway job and pin their code, then install immutable releases behind an atomic `current` pointer. Add bounded worker termination and truthful ledger reconciliation before considering a long-lived router with per-release executors. One generation admits new work; the previous generation owns only work already in flight.

**Tech Stack:** Python, macOS launchd/process groups, SQLite cron and session stores, Unix gateway control socket, Telegram polling/token locks, existing `scripts/run_tests.sh` and `./bin/ci` gates.

---

## Baseline and contract

This was written as a **fork plan** before implementation; [Shipped Status](#shipped-status) records what landed. The maintained fork `0xble/hermes-agent` `main` is the implementation base; the runtime installation and source checkout are distinct ([runtime ownership](runtime-ownership.md)). Before S1, `cron/scheduler.py::_launch_external_cron_worker` used `restart_safe_gateway_child_argv`; on non-Linux that resolver returns `in_process` (`tools/process_registry.py`), so a macOS launchd gateway does not get an external restart-safe cron worker. Linux's systemd transient-scope model cannot be copied to macOS: `launchctl bootout` terminates the job process group, but a `start_new_session` child and double-forked `setsid` grandchild can survive outside that group. Design the macOS worker boundary and explicit kill semantics around that topology, without claiming bootout alone reaps all descendants.

The profile-local `cron/executions.py` ledger records attempt owner PID/start fingerprint and immutable terminal states; it is **not a retry queue**. The current cron inactivity watchdog is idle-based, not a hard wall-clock cap. Scheduler tick locking, `pending_slot`/`scheduled_instant` deduplication, profile scope, and delivery ownership remain authoritative ([cron contract](../cron/AGENTS.md)). Current restart/delegation policy can wait or offer explicit parent-driven recovery, but does not provide uninterrupted overlapping execution ([delegation restart](delegation-restart.md)). The gateway's control socket presently supports identity/status/pause-for-update; it is a candidate coordination seam, not yet a handoff protocol. Upstream's open [structured safe restart PR #71876](https://github.com/NousResearch/hermes-agent/pull/71876) addresses agent-request coordination, not evidence that release pinning or two-generation handoff already exists. Recheck upstream and fork source before each implementation slice.

**Global invariants:** Never automatically retry an interrupted execution, chat turn, or delegation. Preserve one admitted owner per event/occurrence and one active Telegram poller per token; require a receipt from the owning process before acknowledging forwarded input. Preserve both gateway busy-message guards, identity/authorization and per-profile secret scope, prompt-cache stability, turn alternation, and existing durable delivery semantics. Shared databases and `~/.hermes/plugins` must remain readable and writable by both `current` and `previous` during overlap or rollback; use additive/backward-compatible migrations and dual-version contract tests, never a destructive migration during promotion. Do not infer a live runtime revision from source `HEAD`.

## S1 — macOS cron run survives gateway restart

**Dependency:** None. **Observable result:** A launchd-managed gateway can stop/restart while its active cron run continues, with its one scheduled occurrence still owned by that run. Extend the existing dispatch and handoff path in `tools/process_registry.py`, `cron/scheduler.py`, `cron/scheduler_detached_worker.py`, and relevant `tests/cron/` and macOS-marked process tests. Spawn a session-detached worker outside the launchd job's process group, with pinned profile scope, explicit startup acknowledgement, owner PID/start fingerprint, and durable state before gateway release. Do not equate detachment with an unlimited lifetime or use a bare PID as authority. A separate supervised termination strategy must reach descendants that escape through `setsid`; verify the actual macOS process topology, including double fork, rather than faking `sys.platform`.

**Acceptance:** On macOS, an actual launchd bootout/re-bootstrap during a long active cron worker leaves it running exactly once and able to finish and deliver; no second tick dispatches the occurrence. A failed launch/ack does not silently mark success or lose the claimed slot. Prove profile A→B→A scoping and Linux systemd behavior remain unchanged. Run focused tests with `scripts/run_tests.sh` and a disposable-profile launchd integration test. **Containment:** If a restart-safe worker cannot be established, fail visibly before claiming seamless behavior; keep the current restart/drain path available. This slice does not change installation layout or chat handoff.

## S2 — immutable code and reversible promotion

**Dependency:** S1. **Observable result:** A running worker continues importing the code it started with while a new gateway boots from another release. Install complete releases under `releases/<sha>/`, building each virtual environment at its final release path with a warm dependency cache. Changed dependencies require an isolated compatible environment, never mutation of an environment still used by a live release. Point `current` atomically at the candidate only after staging and verification; retain `previous` and three rollback-capable releases (do not prune a release referenced by a live gateway/worker or recovery receipt). Pin executable, working directory, import path, and release SHA at worker launch so a pointer flip cannot change its imports mid-run. Keep profile state and `~/.hermes/plugins` shared, not duplicated into releases.

Likely surfaces: `hermes_cli/update_cmd*.py`, `hermes_cli/gateway_launchd.py`, install/rollback scripts, runtime receipt tests under `tests/hermes_cli/` and `tests/scripts/`. Reconcile existing updater/snapshot and launchd service contracts rather than adding an independent updater. **Acceptance:** Promote release B while an A worker runs, verify A's actual loaded code SHA and B's gateway SHA separately; flip back to A on a staged candidate failure. Test unchanged/changed dependency paths, atomic-pointer crash points, three-release retention, live pin protection, and a consistent-copy schema rehearsal against both versions. **Containment:** No pointer flip on failed staging; retain the previously healthy release and receipts. No gateway activation follows merely from publishing this plan.

## S3 — bounded workers, delivery, and honest recovery

**Dependency:** S2. **Observable result:** A detached cron run has a hard wall-clock limit and its terminal outcome is recorded correctly whether or not a gateway is up. Introduce a configurable finite hard timeout distinct from the existing inactivity and script limits; terminate the verified worker's whole owned process tree/session, including escaped descendants, then record the observed timeout once. Extend `cron/executions.db` additively with immutable code SHA and execution identity; record delivery independently from model/run completion. The worker must enqueue durable outbound delivery when adapters are unavailable, and the next eligible gateway must deliver through the owning profile without inventing a new run. Reconcile startup ledger rows with live detached workers by verified identity and handoff state: a **live** detached worker stays `running`, never `unknown` merely because its gateway died; a proved-dead owner can transition according to existing immutable terminal rules. Do not replay external side effects, retry the occurrence, or turn ambiguous status into success.

Likely surfaces: `cron/executions.py`, `cron/scheduler.py`, `cron/delivery_queue.py`, worker termination and matching process tests. **Acceptance:** Gateway-down completion queues exactly the eligible delivery and drains it after restart; duplicate drain is suppressed by durable receipt. Live owner survives restart reconciliation without `unknown`; PID reuse and unreadable start-time fingerprint fail closed. Hard timeout kills a `setsid` grandchild and records one failure; a past terminal row stays immutable. Exercise real SQLite/profile boundaries with `scripts/run_tests.sh tests/cron/`, plus macOS detached-process integration. **Containment:** Missing reliable process identity or delivery receipt blocks destructive reconciliation, retains inspectable state, and never triggers automatic rerun.

## S4: Router And Per-Release Executors

**Dependency:** S3. **Status:** Design, not an implemented handoff. S2 still reloads the monolithic gateway. The split is opt-in (`gateway.router_executor.enabled: false` by default), per profile and transport. An unsupported adapter stays on the existing monolithic route; it must never accidentally share a polling token with a router. The first implementation targets Telegram. Keep the global invariants above, especially one admitted owner, no automatic retry of an interrupted execution, and prompt-cache stability.

### Process Boundary And Ownership

A small long-lived **router**, pinned to its own immutable release and separately supervised launchd label, owns Telegram's only polling loop/token lock, transport authorization, canonical profile/session identity, input admission and user-visible send/edit APIs. Extract adapter lifecycle and routing from `gateway/run_adapters.py`, `gateway/run_inbound.py`, `gateway/platforms/base.py` and the Telegram adapter (`plugins/platforms/telegram/`); keep platform-specific callback and media semantics at the router. The current gateway control socket (`gateway/control_socket.py`) is a single-line synchronous JSON status/identity seam, not a streaming RPC or safe overlapping owner. Add separate versioned router/executor endpoints and a bounded authenticated local channel with profile-scoped socket permissions. Never let two processes bind or unlink the same control path. `gateway/status.py` must report router identity and every live executor generation separately, including PID/start fingerprint and release SHA, not silently collapse them to one gateway PID.

Each **executor** is separately supervised like the S1 detached cron worker, launched with executable, cwd and import path pinned to `releases/<sha>` by `hermes_cli/immutable_releases.py` and `hermes_cli/gateway_launchd.py`. It owns `gateway/run_turn.py`, `gateway/run_turn_runner.py`, agent/session state, approval resolution, busy-turn policy (`gateway/run_busy.py` and `gateway/run_inbound.py`), `tools/async_delegation.py`, tool subprocesses and generation-scoped dispatch. Router owns presentation and transport; executor requests output over the channel. `gateway/platforms/base.py` currently holds a second active-session guard with command bypass, clarify, pending/debounce FIFO and late-arrival reconciliation. Do **not** split that guard by approximating it in the router: router durably sequences events and the owning executor runs both busy guards against its session state. `/stop` and `/new` bypass and plaintext/inline approval must still reach that owner. Do not move the existing user-facing command behavior or authorization to a different trust boundary silently.

### Protocol And Durable State

Use a per-profile SQLite WAL coordinator (additive migrations, five-second busy timeout and explicit transaction boundaries) as the one durable answer for `session_key → generation`, delegation parent and generation, admitted event, dispatch epoch, drain state and outbox cursor. Router assigns monotonically increasing `event_seq` within each canonical session and an idempotency key `(profile, platform, transport_event_id, event_kind)`, with a durable fallback ID for synthetic events. On Telegram redelivery, return the original result. In one transaction, persist the admission and the generation claim, then reply `accepted(event_id, owner_generation, seq)` only after the executor durably accepts it. A router-local enqueue or socket write is **not** executor acceptance. Commands requiring immediate handling receive an explicit disposition (`accepted`, `unauthorized`, `busy`, `stale-owner`, `unavailable`); queued follow-ups retain identity, security metadata and ordering, rather than merging distinct text turns. Same-session events run in sequence, while different sessions may run concurrently. Reject gaps and stale epochs, do not infer acceptance from a timeout. A recovery reader resolves ambiguous acceptance by querying the durable event row, not by replaying side effects.

Channel messages include `admit`, `accepted`, `stream_edit`, `final_reply`, `approval_prompt`, `approval_answer` (`/approve` and `/deny`), `steer`, `stop`, `follow_up`, `busy_ack`, `typing`, `progress`, `health` and `drain`. Carry session/turn/delegation IDs, source identity, original platform event ID, owner epoch, per-turn sequence and idempotency key. Router verifies the sender's configured authorization before dispatch, executor rechecks the canonical source and ownership before affecting its session. Approvals are scoped to the original pending approval and turn; stale, repeated or foreign answers are refused. Steer and stop are serialised with the running turn; a stop is not a new user turn. Typing has a short expiry and can be coalesced, but no final, approval, attachment or accepted input can be lost or reordered. Streaming edits preserve platform message IDs and edit order. Failed router connection means the executor keeps running but emits only durable output; failed executor means the router refuses new admission to its owned session, leaves accepted inputs recorded, reports unavailable and waits for a proven owner/recovery disposition. Never reroute the old session to B while A might still execute it.

**S4.1 outbox:** First implement this contract inside the monolithic gateway, with its turn runner as the producer; S4.2 moves that producer into the executor without changing the schema. Before any user-visible send, the producer commits an ordered `outbox(turn_id, sequence, type, payload, idempotency_key, owner_epoch)` row. Under the split, the router alone sends/edits and records platform receipt (`message_id`, send/edit status) before advancing the cursor. On router replacement it resends unsent rows in order; duplicate sends after a transport success but before receipt are **ambiguous** unless that transport supports idempotent delivery or can reconcile a stable provider message ID. Therefore the honest guarantee is exactly-once *local enqueue and acknowledged dispatch*, not unconditional exactly-once Telegram delivery. An ambiguous send is held for reconciliation or explicitly reported, not blindly replayed as a second final reply. Preserve existing cron delivery queue as a separate producer through the same router egress where applicable, without replaying a cron occurrence.

### Fencing, Handover And Recovery

Acquire a generation lease by an atomic compare-and-swap transaction with strictly increasing epoch and verified process fingerprint; refresh it only while healthy. The durable claim for an active session/delegation is immutable until its owner completes, is proved dead, or is explicitly interrupted once. Generation A in `draining` cannot claim a new session, new cron occurrence, or new kanban card; it still receives ordered inputs for its already owned turns and delegations. Generation B claims only unowned new work after its health/readiness proof. Every executor-side dispatch and outbox write checks the epoch and claim in the same transaction as its durable effect. Database fencing cannot roll back an already running external tool: never transfer that active execution or automatically retry it. Cron's `cron/executions.db` attempt identity and pending-slot contract remain authoritative; kanban claim and cron tick each require the same single dispatch owner epoch and must refuse ambiguous ownership. Separate legacy dispatcher paths that cannot prove the epoch remain disabled under the flag.

S4.3 starts B pinned to a staged release while A and the router keep working. B has no polling token. Within **60 s**, prove process identity, code SHA, compatible DB/plugin read/write, local admission plus output through the router, and single cron/kanban dispatcher ownership. Commit the active admission/dispatch generation to B, then mark A draining. The router remains the sole Telegram poller throughout. A finishes owned work for up to **two hours**; at the cap, stop its admission, fence its lease, interrupt each unfinished turn/delegation once with original owner and reason, retain recovery evidence, and do not retry. Hold A's release (and `previous`) until no live process, unacknowledged output, claim or recovery receipt references it. Promotion moves `current` only in the updater's existing transactional switch; router release is independent. If B fails health, fence B and route *new* work back to healthy A, restore `current`/`previous` using the existing rollback transaction and leave A-owned work alone. Work accepted by B remains B-owned until it completes or is explicitly interrupted; do not silently transfer it to A. If neither is healthy, admission fails closed with inspectable state rather than claiming rollback success.

Router crash/replacement recovers its lease, last transport offset and durable outbox; the executor continues, reconnects to the new router and flushes ordered output. A dead executor's lease is not stolen on mere heartbeat delay: verify PID/start fingerprint and supervisor state, mark only proven-dead work interrupted once, preserve ambiguous tool effects and offer the existing explicit continuation path. A router cannot use its memory of active sessions as the authority. The existing `gateway/run_shutdown.py` interruption and `tools/async_delegation.py` persistence paths must be adapted rather than bypassed. The fallback, if extraction is rejected, remains the original two-gateway overlap with a token-polling handoff, generation-specific endpoints and the same fencing/outbox contract; it does not eliminate the hard admission or delivery problem.

### Rollout, Guardian And Acceptance

S4.1 (durable outbox and admission receipts) precedes S4.2 (router/executor extraction, protocol and fencing), then S4.3 (staged release promotion and drain), then G1 (guardian). Keep each slice behind the default-off config gate and in a separate PR. S4.1 touches `gateway/run_turn*`, `gateway/platforms/base.py`, Telegram delivery and SQLite tests: prove queue→send→receipt, router death before send, ambiguous success, duplicate input, FIFO/edit ordering, profile A→B→A and exact attachment/approval delivery. S4.2 touches `gateway/run_adapters.py`, `gateway/run_inbound.py`, `gateway/run_busy.py`, `gateway/control_socket.py`, `gateway/status.py`, Telegram transport, `tools/async_delegation.py`, cron/kanban dispatch and tests: prove both busy guards, approval, steer, stop, queued follow-up, late callback, one token poller, one owner for every claim and a router-only replacement while a real executor continues. S4.3 touches updater, launchd, `immutable_releases.py`, shared schema/plugin rehearsal and process tests: stage B in under 60 s, A drains under injected two-hour clock, failed B health rolls new admission back to A, active B work is never stolen and release pinning survives promotion. G1 is a separate minimal launchd job, not an executor thread: detect an *unloaded* intended gateway/router service, bootstrap its known-good plist, and roll back a failed release switch only after proving the old release/health and checking the switch receipt. Use finite attempts, a lock and receipts to avoid repair loops or fighting an intentional stop. It must not silently repair a corrupt pointer with source-venv fallback.

Live update acceptance uses one disposable-profile rehearsal followed by a separately authorized real update: (a) A chat turn continues on A, (b) a delegation continues on A, (c) B answers a new session, (d) approval reaches A once, (e) follow-up/steer/stop and both busy guards work, (f) exactly one cron occurrence and kanban claim dispatch, (g) B failure routes only new work back to A, (h) identities, code SHAs, DB/plugin compatibility and user-visible delivery receipts are read back. Separately kill and replace only the router during an executor turn, inject failures at every admission/receipt/lease boundary, test G1 against an unloaded service and intentional stop, and soak with concurrent sessions and a promotion while watching duplicate final replies, unknown owners, missing receipts and leaked generations. Run focused tests, exact-SHA `./bin/ci gate <sha>`, schema rehearsal on a consistent copy, and actual macOS launchd/Telegram E2E before activation. Landing code does not authorize switching this live gateway.

### Invasiveness Assessment And Recommendation

**Estimate, not a measured diff:** roughly 25–40 production files, 4,000–8,000 changed lines plus 3,000–6,000 test lines across four PRs. The riskiest seams are the 5,008-line `gateway/platforms/base.py` active-session and presentation coupling, 6,214-line `gateway/run.py` orchestration, Telegram callback/polling ownership, synchronous control socket, in-memory agent/approval/delegation registries, and shared SQLite/plugin compatibility. The baseline supports a real cost, but cannot prove that most of the 387 near-stop markers are caused by planned replacements. **Recommendation: feasible but not justified for immediate S4.3 implementation. Build S4.1 and a small S4.2 disposable-profile spike first; proceed to the full split only if real turn, delegation, approval and outbox E2E can run with one poller and no duplicate send. Otherwise stop, retain S1–S3 and use the original two-gateway overlap only if its equally hard token/ownership proof passes. Do not equate the two-hour cap or SQLite receipts with exactly-once external effects.**

### S2 settled decisions (implementation contract)

- **Virtual environments are per release and built in place.** Each `releases/<sha>/` owns `.venv`, built at its final path from that release's lockfile (`uv sync --frozen`). Do not physically clone or relocate a venv: shebangs, activation scripts, and metadata can retain the old absolute path. A warm-cache build on this Mac in a disposable source export took 1.60s (`/usr/bin/time -p mise x uv@0.12.13 -- uv sync --frozen --python <base-interpreter>`); this is a measurement, not a service-activation result.
- **Plugins remain shared.** `HERMES_HOME/plugins` is owned and changed independently by agentkit. Promotion does not modify it. Staging copies the relevant plugin tree and config into a disposable profile and imports enabled plugins with the candidate interpreter (without calling `register()`); an import failure aborts before the `current` pointer changes. Agentkit must keep plugin releases compatible with both current and previous Hermes releases; that compatibility contract is outside S2.
- **Promotion order is transactional.** Stage the fetched source, private venv, and plugin smoke; write `previous` to the old target; atomically replace `current`; then retain `current`, `previous`, three rollback-capable releases, and every release pinned by a live process or receipt. A failed stage leaves the old pointer untouched.
- **Runtime pinning.** launchd definitions resolve program, cwd, venv, and import path through `current`; a detached cron worker resolves `current` once at launch and pins the resulting release path for its executable, cwd, and `PYTHONPATH`. `~/.hermes/hermes-agent` remains the git source checkout and is not replaced by a release.
- **Migration and rollback.** The first promotion creates the current-HEAD release and updates the existing launchd plist through `hermes_cli/gateway_launchd.py`; `hermes update --rollback` atomically points `current` at `previous` and uses the existing restart/report/receipt path. A migration rollback points the plist back to the source checkout. Do not activate this migration on the live install without the parent owner's separate authorization.

**Remaining risks.**

- An in-flight chat turn is still interrupted by a restart (`restart_drain_timeout: 0`); it auto-resumes with a restart note, but its tool call is not retried. Background delegations of that gateway are interrupted too. Removing this is S4.
- An unloaded or corrupted launchd service after a failed switch needs an operator repair from a shell outside the gateway. A corrupt `current` pointer makes `get_python_path()` fall back to the source venv silently. The S2 config keys have no type/range validation.
- In a rare no-pull catch-up where checkout repair is incomplete, the receipt can read `success` while the command exits 1 (review finding on #211). `release-last-txn.json` persists, so a repeatedly failing fleet verification on the credited label never falls back to a relaunch; `hermes gateway restart` remains the remedy.
- Manually stopped cron runs still record a misleading "scheduler restarted" `unknown`, and manual runs are not kill-protected. A double-forked descendant that escapes the worker session is not swept, and a kill between ledger commit and delivery enqueue leaves `unknown` with no resend.
- The full unscoped update path can only be proven live; disposable rehearsals cover it with throwaway launchd labels.
